        Supported formats, conversion method and recovery

        Collection coverage

        The reader was checked against the supplied 51 beta and 100 final ALS files. It traverses root and layer machine vectors, base/layer states, categories, transition groups and supported interaction, aim, wall-run and swing resources. This does not imply support for every .ALS variant or every platform. Non-empty layer transitions, rule post-actions, force-transition conditions and pointer-valued parameter types outside the observed profile remain rejected.

        Reference method

        The tool constructs temporary correspondences from the files loaded in this session. It matches machine IDs, state/category identity hashes, unambiguous transition signatures and resource names/hashes. Unique or strongly dominant record matches resolve ordinary IDs. Resource class splits are handled per resource rather than with a global byte replacement. In a collection, every usable same-name pair contributes evidence; a single explicit pair is also supported. No earlier byte map, generated ALS or preset character ID table is required.

        Forward and reverse are separate analyses

        Beta → final reads the final collection as its target. Final → beta reads the beta collection as its target and learns that direction anew, rather than blindly reversing a dictionary. Many-to-one type changes can make the reverse ambiguous. A file with any unresolved identifier is blocked, not partially converted and disguised as a successful output.

        Resource adaptation is not lossless by itself

        Swing headers can expand or shrink by 48 verified zero bytes. Aiming resources can switch between 96-byte/four-slot and 72-byte/two-slot layouts. The latter requires approval because the matching target payload replaces the source animation hashes and aim limits. The source resource name/hash and overall record ordering remain intact. Original replaced bytes and every edit offset are saved in JSON, so the exact source is recoverable from the converted file and its report. Ordinary forward/reverse re-conversion is not a byte-identical round trip.

        Inputs and privacy

        Load individual .ALS files, a folder, or a standard ZIP using stored/DEFLATE compression. Extract .7z archives first, or load the supplied ZIP copies. ZIP64, split and encrypted ZIPs are refused. Limits: 16 MiB per ALS, 128 MiB per collection, and 2000 input entries. Files are processed in browser memory using bundled JavaScript; there are no network requests, external scripts or backend. Original files are never overwritten.

        Reports and safe use

        The output ZIP contains only converted ALS files, their detailed JSON/text reports and a batch manifest. Keep the original files and review the skipped list. Every built file is re-parsed and checked for identifier writes, retained records, local indices, filter thresholds, resource shifts and exact restoration from the log. These checks do not verify whether the target game executable implements every retained state or has the required animations. Game-runtime compatibility remains untested.
